# Lab 05 — Solution

Measured on Docker Desktop for Mac (Docker Engine 29.9.2, Compose 5.6.1, Apple Silicon). Where Linux is different, it says so.

## Two kinds of error

When one container can't talk to another, the error tells you which kind of problem you have:

| What you see | What it means | What to check |
|---|---|---|
| `Name does not resolve` (Python on Alpine) · `bad address` (`wget` and `ping` on Alpine) | Nothing could turn the name into an address | Is the other container running? Is it on the same network as the caller? Is that a network you created, not the default one? Is the name spelled right? |
| `Connection refused` | The name worked. The call reached an address, and nothing was listening on that port | Is the caller using `localhost`? Is it using the published port instead of the container's own port? |

Other images use other words for the first kind. Python on a Debian-based image, like `python:3.12-slim`, says `Name or service not known`.

## Part 1: two containers, side by side

```
$ docker run --rm --name reception switchboard-app wget -qO- records:8000
wget: bad address 'records:8000'
$ docker exec records hostname -i
172.17.0.2
$ docker run --rm --name reception switchboard-app wget -qO- 172.17.0.2:8000
records is open
```

`records` is there, and it answers. `reception` just can't find it by name.

### Why the name doesn't work

A container turns names into addresses by asking a DNS server: think of it as a phone book. `/etc/resolv.conf` says which one:

```
$ docker exec records cat /etc/resolv.conf
# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 192.168.65.7

# Based on host file: '/etc/resolv.conf' (legacy)
# Overrides: []
```

`docker run` without `--network` puts a container on the **default** network, called `bridge`. There, the container gets a copy of your computer's DNS settings (`192.168.65.7` is Docker Desktop's link to them; on Linux you see your server's own). That phone book knows websites. It doesn't know your containers. Docker's docs: "Containers on the default bridge network can only access each other by IP addresses, unless you use the `--link` option, which is considered legacy."

### Why not just use the number?

```
$ docker stop records
$ docker run -d --name pharmacy -e NAME=pharmacy switchboard-app
$ docker start records
$ docker run --rm --name reception switchboard-app wget -qO- 172.17.0.2:8000
pharmacy is open
```

A container gets its address when it starts. When `records` stopped, its address was free again, so the next container to start, `pharmacy`, got it. `records` came back with a new one. The old number now reaches the wrong patient. (On your computer the numbers can come out in a different order, so nobody may answer at all. Either way, the old number is no good.)

Docker's docs: "Docker assigns container IP addresses dynamically from the network's subnet each time a container starts so they are not persisted across restarts or recreations. This means you should always reference services by name, not IP address."

### The fix: a network you create

```
$ docker network create clinic
$ docker network connect clinic records
$ docker run --rm --name reception --network clinic switchboard-app wget -qO- records:8000
records is open
$ docker exec records cat /etc/resolv.conf
# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 127.0.0.11
options ndots:0

# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(192.168.65.7)]
# Overrides: []
# Option ndots from: internal
```

`docker network connect` adds a running container to a network, with no restart. Now the phone book is `127.0.0.11`: Docker's own DNS server, inside every container on a network you create. It knows every container on that network by name. For any other name, it asks the outside DNS server, the one in the `ExtServers` line. Docker's docs: "The embedded DNS server address is `127.0.0.11`." and "The embedded DNS server forwards external DNS lookups to the DNS servers configured on the host."

Compose does this for you. `docker compose up` prints `Network switchboard_default Created`: every Compose project gets its own network, so its services can call each other by service name.

Clean up Part 1:

```bash
docker rm -f records pharmacy
docker network rm clinic
```

## Part 2: the chart

```
$ curl localhost:8080
records    http://localhost:8000    [Errno 111] Connection refused
pharmacy   http://pharmacy:8082     [Errno 111] Connection refused
billing    http://billing:8000      [Errno -2] Name does not resolve
```

| Call | What the board says | The cause | The fix |
|---|---|---|---|
| `records` | `Connection refused` | `RECORDS_URL` says `localhost`, and inside `reception`, `localhost` is `reception` itself | `RECORDS_URL: http://records:8000` |
| `pharmacy` | `Connection refused` | `PHARMACY_URL` uses the published port, 8082. Containers call each other on the container's own port | `PHARMACY_URL: http://pharmacy:8000` |
| `billing` | `Name does not resolve` | `billing` has a `networks` line, so it's only on `private`. `reception` is only on `default` | Put `reception` on both networks: `default` and `private` |

## Patient 1: `records`, calling yourself

`RECORDS_URL` is `http://localhost:8000`. Inside a container, `localhost` means that same container. So `reception` is calling its own port 8000, where nothing listens. `records` is a different container, with its own address.

You'll meet this one at work. On your laptop, every app runs on `localhost`, so the settings say `localhost`. Put each app in its own container, and those settings break.

Ask for the right address from inside the caller:

```
$ docker compose exec reception getent hosts records
172.20.0.4        records  records
```

**The fix:** call the service by its name:

```yaml
      RECORDS_URL: http://records:8000
```

```bash
docker compose up -d reception
curl localhost:8080
```

### When the thing you need runs on your Mac

Then neither `localhost` nor a service name will find it. Docker Desktop gives your Mac a name: `host.docker.internal`. Try it: open a second terminal in this lab's folder, and run the clinic app on your Mac itself (it needs Python 3):

```
$ NAME="your Mac" python3 app/app.py
your Mac: listening on port 8000
```

Back in the first terminal:

```
$ docker compose exec reception wget -qO- localhost:8000
wget: can't connect to remote host: Connection refused
$ docker compose exec reception wget -qO- host.docker.internal:8000
your Mac is open
```

The server on your Mac logs the call as coming from `127.0.0.1`: Docker Desktop delivers it to your Mac's own `localhost`. That's why, on a Mac, it works even for a server that listens only on `127.0.0.1`. Stop the server with Ctrl+C.

On Linux, Docker doesn't add that name by itself. Add it in `compose.yaml`:

```yaml
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

Docker's docs: "On Linux, `host-gateway` resolves to the host's IP on the default bridge network." So on Linux, a program that listens only on `127.0.0.1` won't hear the call. It has to listen on that address too, or on `0.0.0.0`. (Not run here: this lab was measured on a Mac.)

## Patient 2: `pharmacy`, the outside number

`PHARMACY_URL` is `http://pharmacy:8082`. The name is right. The port comes from the pharmacy's ports line:

```
$ docker compose ps pharmacy --format "table {{.Service}}\t{{.Ports}}"
SERVICE    PORTS
pharmacy   0.0.0.0:8082->8000/tcp, [::]:8082->8000/tcp
```

Someone opened http://localhost:8082 in a browser, it worked, and they copied the number. But the left number is a door on **your computer**. Containers on the same network call each other directly, on the right number:

```
$ docker compose exec reception wget -qO- pharmacy:8082
wget: can't connect to remote host (172.20.0.2): Connection refused
$ docker compose exec reception wget -qO- pharmacy:8000
pharmacy is open
```

Docker's docs: "Networked service-to-service communication uses the `CONTAINER_PORT`. The host port is only used when accessing the service from outside the network."

**The fix:**

```yaml
      PHARMACY_URL: http://pharmacy:8000
```

```bash
docker compose up -d reception
curl localhost:8080
```

`pharmacy` doesn't even need its ports line for `reception` to reach it. A ports line is only for reaching a container from outside Docker, like your browser. Delete it, run `docker compose up -d`, and the board still says `pharmacy is open`.

## Patient 3: `billing`, the other building

```
$ docker compose exec reception getent hosts billing
$ docker compose ps billing --format "table {{.Service}}\t{{.Status}}"
SERVICE   STATUS
billing   Up 53 seconds
$ docker ps --filter name=switchboard --format "table {{.Names}}\t{{.Networks}}"
NAMES                     NETWORKS
switchboard-reception-1   switchboard_default
switchboard-records-1     switchboard_default
switchboard-pharmacy-1    switchboard_default
switchboard-billing-1     switchboard_private
```

`getent` prints nothing: the name is unknown. `billing` is up, so that's not why. The NETWORKS column is: `billing` is alone on `switchboard_private`.

`billing` has a `networks` line, to keep it away from the others. Here's the trap: a `networks` line doesn't **add** a network. It **replaces** the default one. Docker's docs: "Services without an explicit `networks` declaration are connected by Compose to this `default` network." A service **with** one joins only what it lists. Each network has its own names, so from `default`, `billing` doesn't exist.

**The fix most people try first:** give `reception` the private network:

```yaml
    ports:
      - "8080:8080"
    networks:
      - private
```

```
$ docker compose up -d reception
$ curl localhost:8080
records    http://records:8000      [Errno -2] Name does not resolve
pharmacy   http://pharmacy:8000     [Errno -2] Name does not resolve
billing    http://billing:8000      billing is open
```

Billing works, and the other two broke. It's the same trap again: `reception`'s new `networks` line replaced **its** default network. Now `reception` is on `private` only, with `billing`, and it can't see the others.

**The real fix:** list both:

```yaml
    networks:
      - default
      - private
```

```
$ docker compose up -d reception
$ curl localhost:8080
records    http://records:8000      records is open
pharmacy   http://pharmacy:8000     pharmacy is open
billing    http://billing:8000      billing is open
$ docker ps --filter name=switchboard --format "table {{.Names}}\t{{.Networks}}"
NAMES                     NETWORKS
switchboard-reception-1   switchboard_default,switchboard_private
switchboard-records-1     switchboard_default
switchboard-pharmacy-1    switchboard_default
switchboard-billing-1     switchboard_private
```

## Step 4: billing is still private

```
$ docker compose exec records wget -qO- billing:8000
wget: bad address 'billing:8000'
$ docker compose exec pharmacy wget -qO- billing:8000
wget: bad address 'billing:8000'
```

Only `reception` sits on both networks, so only `reception` can call `billing`. That's what the `networks` line was for.

## One more cause: the container isn't running

The phone book only lists containers that are running:

```bash
docker compose stop billing
curl localhost:8080
docker compose start billing
curl localhost:8080
```

While `billing` is stopped, its line says `Name does not resolve`, exactly like the network problem. So when a name doesn't resolve, check that the container is up first. You'll meet this with databases: when the database container has crashed, the app says it can't find the database's name.

## The interview answer

> "Two containers can't talk to each other. How do you debug it?"

I read the error first. If the name doesn't resolve, I check that the other container is running, and that both are on the same network, one I created, not the default one. If the connection is refused, the name worked, so I check the caller isn't using `localhost`, and that it calls the container's own port, not the published one. I test from inside the caller, with `getent hosts` and `wget`.
